# Dependency updates

This document holds reusable upgrade procedures and active constraints. Update
entries in place and remove resolved ones, linking the PR or upstream evidence
and the condition for revisiting each exception. Put each run's version inventory,
audits, validation, warnings, previews, and held groups in its upgrade PR; do not
append a dated journal here or in README. Existing advisory observations are
recheck targets, not a fresh audit. Keep private logs, credentials, plans, and
state out of public reports.

The frontend, backend-v2, api-shared and website are Bun workspaces of the root
`package.json`, which also owns the development tooling, including the
exact-pinned `@a2f0/agent-tool`. Each package declares its own dependencies in
its `package.json`; the root holds the one `bun.lock`, and the install
settings, `overrides` and `trustedDependencies` that apply to every package
(Bun reads those only from the root `package.json` and `bunfig.toml`). Change a
package's dependencies in its manifest (for example
`bun run agent-tool bun add <name>@<version> --cwd packages/<package>`), commit
the root `bun.lock` with that manifest, and validate every package the lockfile change reaches; a
dependency shared with another package can resolve differently there too.
Consumers reference api-shared as `workspace:*`, a link to its directory, so
its edits need no reinstall. Preserve minimum release age and verify that
unrelated package identities did not change.

The root `.mise.toml` pins Bun 1.4.3 and Node 24.22.1 for development and CI.
Keep its Bun pin and every package's `packageManager` declaration together. Keep its Node pin, frontend `engines.node` and Node types compatible.
Terraform retains its specialized setup.
Preserve the frontend's exact dependency pins and one-day minimum release age.
The root `bunfig.toml` applies that age policy to every package's new
resolutions. An offline install lacking release timestamps does not justify
disabling that policy.

## Compatibility groups

- Keep React, React DOM and their types compatible with MUI and the test renderer.
- Upgrade Vite with its React, HTML, PWA and analysis plugins. Run both staging
  and production builds, the unit suite and the WebdriverIO suite.
- Upgrade WebdriverIO with every `@wdio/*` runner, framework and reporter, browser
  driver tooling and the video reporter. A permissive peer range cannot replace
  a working browser run.
- WebdriverIO stays on the latest 9.x group while `wdio-video-reporter` 6.2
  depends on the 9.x globals, reporters, logger, and types. Revisit 10.x when
  the reporter supports it, then run the full browser suite and failure-video
  integration; do not force a mixed runner/reporter major. See the
  [reporter manifest](https://github.com/webdriverio-community/wdio-video-reporter/blob/v6.2.0/package.json).
- MSW 3 uses the [migrated entrypoints](https://mswjs.io/docs/migrations/2.x-to-3.x):
  HTTP exports come from `msw/http` and utilities have individual entrypoints.
  Preserve `onUnhandledFrame` and await `worker.stop()` when adding shutdown.
  Regenerate `public/mockServiceWorker.js` with the chosen version,
  then test the HTTP contracts and browser interception on the actual Node and
  browser runtimes.
- Keep the backend's `@cloudflare/vitest-plugin`, Wrangler, and Miniflare
  aligned. Plugin 1.4.6 supports Vitest 5; keep coverage-istanbul on the exact
  same Vitest release and run both backend coverage gates after changing them.
- The website's `@astrojs/check` 0.9.12 supports TypeScript 5 and 6. Keep its
  TypeScript 6.0.3 pin until the checker supports TypeScript 7's compiler API.
- Match each Biome schema URL to its CLI. Native optional packages in the Bun
  lockfile belong to the CLI release and must be regenerated by Bun.

Frontend TypeScript 7.0.2 still needs `compile`'s `--force` workaround documented
in its `AGENTS.md`. Do not remove it on the strength of a clean incremental run.
`commitlint.config.mts` reads subject types/length from `agent-tool.json`.
Full commitlint rules still run in commit-msg and the required PR-title check;
the shared tool's data-only subject checks do not replace those additional rules.

## Transitive security checks

Audit the root lockfile, which covers every package. Prefer an owner upgrade or
a targeted Bun refresh within the owner's supported range. Keep the existing
Puppeteer and serialize-javascript overrides, which the frontend needs and the
root `package.json` declares, until their documented regression and audit
conditions allow removal.

Known constrained transitive dependencies include:

- The frontend's micromatch and chokidar graph includes Braces 3.0.3;
  [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
  has no verified published fixed version. The patterns are repository tooling
  inputs; retain the constrained graph until its owner offers a supported fix.
- Drizzle Kit's legacy `@esbuild-kit/core-utils` graph still includes esbuild
  0.18.20, affected by
  [GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99).
  It is development tooling; do not expose its development server to untrusted
  websites or force an unsupported esbuild major beneath it.
- Updating http-cache-semantics from 4.2.0 to 4.3.0 does not establish that
  [GHSA-ch52-4w7c-c8xp](https://github.com/advisories/GHSA-ch52-4w7c-c8xp)
  is fixed. Its shared Set-Cookie and proxy-revalidate cases remain storable
  with a zero lifetime, yet accept `max-stale`. Astro's remote-image client
  uses `storable()` and `timeToLive()`, expires those responses immediately,
  and does not pass `max-stale`; these library cases do not establish website
  exposure. Keep the upstream advisory unresolved and check actual callers
  rather than inferring remediation solely from its version range.

Source-map-js 1.2.2's
[release](https://github.com/7rulnik/source-map-js/releases/tag/v1.2.2)
fixes malicious indexed source-map denial of service. Refresh an older
resolution within its owner's supported range with Bun, then rerun the audit.
Report unavailable registry audits and release metadata as coverage limits,
separately from any known unresolved advisories.

## Infrastructure previews

Keep `upload_source_maps: false` explicit in the API and website Worker
configurations, inherited by staging and production. Wrangler 4.150 changed
its deploy default to upload generated source maps; dependency updates must
preserve the existing opt-out unless that upload policy is intentionally changed.

Before a Terraform CLI, provider or module update, use the `.secrets` tier
credentials that `scripts/tf` loads and the real R2 backend for each of `zone`,
`staging` and `production`. Save a full refreshed plan with locking. From
`terraform/`, use `mktemp -d` to create a private directory outside the
checkout, pass its absolute path to
`scripts/tf <stack> plan -input=false -lock=true -out=<private-plan>`, and
redirect `scripts/tf <stack> show -json <private-plan>` to a JSON file there.
Inspect resource actions, drift, checks and deferred changes; reject deletions,
replacements and incomplete evidence. Keep both files private and remove them
after use. Backend-disabled validation and mocked module tests do not prove
production safety.

Before updating Wrangler or its coupled workerd/Miniflare packages, run the
proposed CLI's `deploy --dry-run` for each affected environment. Verify existing
account, Worker, route and binding identities separately: bundling does not plan
remote resources or D1 migrations. Inspect pending SQL and migration semantics
before any application or deployment.

Feature-branch pushes and PR CI do not deploy. Pushes to `main` or `staging`
that change backend-v2, api-shared, the root `package.json`, `bunfig.toml` or
`bun.lock`, or `.github/workflows/backend-v2.yml` can trigger remote D1
migrations and deployment when the repository variable
`BACKEND_V2_DEPLOY` is `true`. Re-read that variable before shipping and require
the same preview and identity checks before the workflow's mutation.
Never apply, deploy, reset data or replace a resource to discover whether an
upgrade is safe.
