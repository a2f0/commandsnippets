# Dependency updates

The root Bun workspace contains only `packages/agent-tool`. The frontend,
backend-v2, api-shared and website each own their `package.json` and `bun.lock`;
install and validate each changed package from its own directory. Reinstall both
API consumers after changing api-shared, as its README describes.
Compare each consumer lock's `file:../api-shared` dependency snapshot with the
owned manifest, including development dependencies and native package versions.
If a normal install retains a stale snapshot, use the supported targeted
`bun update @commandsnippets/api-shared` in each consumer, then validate the
installed source links and run its checks. With a complete verified local cache,
`--offline --ignore-scripts` can refresh the snapshot without running lifecycle
scripts; run their required validation separately. Preserve minimum release age
and verify that unrelated package identities did not change.

Use Bun 1.4.2, matching CI. Frontend tools execute on Node 24.21.0 from its
`.nvmrc`; keep `engines.node`, Node types and CI's version-file input together.
Preserve the frontend's exact dependency pins and one-day minimum release age.
An offline install lacking release timestamps does not justify disabling that
policy.

## Compatibility groups

- Keep React, React DOM and their types compatible with MUI and the test renderer.
- Upgrade Vite with its React, HTML, PWA and analysis plugins. Run both staging
  and production builds, the unit suite and the WebdriverIO suite.
- Upgrade WebdriverIO with every `@wdio/*` runner, framework and reporter, browser
  driver tooling and the video reporter. A permissive peer range cannot replace
  a working browser run.
- MSW 3 requires the [2.x to 3.x migration](https://mswjs.io/docs/migrations/2.x-to-3.x):
  HTTP exports move to `msw/http`, utilities have individual entrypoints,
  `onUnhandledRequest` becomes `onUnhandledFrame`, and `worker.stop()` becomes
  asynchronous. Regenerate `public/mockServiceWorker.js` with the chosen version,
  then test the HTTP contracts and browser interception on the actual Node and
  browser runtimes.
- The backend's `@cloudflare/vitest-plugin` 1.3.0 requires Vitest and its runner
  and snapshot packages on 4.1.x. Keep coverage-istanbul on the same version.
- The website's `@astrojs/check` 0.9.10 supports TypeScript 5 and 6. Keep its
  TypeScript 6.0.3 pin until the checker supports TypeScript 7's compiler API.
- Match each Biome schema URL to its CLI. Native optional packages in the Bun
  lockfiles belong to the CLI release and must be regenerated by Bun.

Frontend TypeScript 7.0.2 still needs `compile`'s `--force` workaround documented
in its `AGENTS.md`. Do not remove it on the strength of a clean incremental run.
Root commitlint's programmatic TypeScript consumers also need validation even
when the compiler CLI passes.

## Transitive security checks

Audit every owning lockfile. Prefer an owner upgrade or a targeted Bun refresh
within the owner's supported range. Keep the frontend's existing Puppeteer and
serialize-javascript overrides until their documented regression and audit
conditions allow removal.

The September 2026 advisory baseline identified these remaining constraints:

- Miniflare's exact Sharp 0.35.4 pin carries
  [GHSA-wq5f-xc86-pv6w](https://github.com/advisories/GHSA-wq5f-xc86-pv6w).
  Sharp 0.35.5 is available, but an override needs native ABI checks and a real
  offline Miniflare Images SVG-to-PNG regression before adoption.
- Miniflare's exact Undici 7.29.0 pin remains affected by the advisories fixed
  in 7.29.1. An owner update is coupled to Wrangler and workerd validation.
- The frontend's micromatch and chokidar graph includes Braces 3.0.3;
  [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
  has no verified published fixed version. The patterns are repository tooling
  inputs; retain the constrained graph until its owner offers a supported fix.
- Drizzle Kit's legacy `@esbuild-kit/core-utils` graph still includes esbuild
  0.18.20, affected by
  [GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99).
  It is development tooling; do not expose its development server to untrusted
  websites or force an unsupported esbuild major beneath it.
- Updating http-cache-semantics from 4.2.0 to 4.3.0 does not establish that
  [GHSA-ch52-4w7c-c8xp](https://github.com/advisories/GHSA-ch52-4w7c-c8xp)
  is fixed. Its shared Set-Cookie and proxy-revalidate cases remain storable
  with a zero lifetime, yet accept `max-stale`. Astro's remote-image client
  uses `storable()` and `timeToLive()`, expires those responses immediately,
  and does not pass `max-stale`; these library cases do not establish website
  exposure. Keep the upstream advisory unresolved and check actual callers
  rather than inferring remediation solely from its version range.

Source-map-js 1.2.2's
[release](https://github.com/7rulnik/source-map-js/releases/tag/v1.2.2)
fixes malicious indexed source-map denial of service. Its supported ranges allow
a targeted lock refresh. Report unavailable registry audits and release metadata
as coverage limits, separately from any known unresolved advisories.

## Infrastructure previews

Before a Terraform CLI, provider or module update, use the SOPS credentials and
the real R2 backend for each of `zone`, `staging` and `production`. Save a full
refreshed plan with locking, inspect its JSON using the workspace's dependency
plan helper, and reject every deletion or replacement. Backend-disabled
validation and mocked module tests do not prove production safety.

Before updating Wrangler or its coupled workerd/Miniflare packages, run the
proposed CLI's `deploy --dry-run` for each affected environment. Verify existing
account, Worker, route and binding identities separately: bundling does not plan
remote resources or D1 migrations. Inspect pending SQL and migration semantics
before any application or deployment.

Feature-branch pushes and PR CI do not deploy. A merge that touches backend-v2 or
api-shared can trigger remote D1 migrations and deployment when the repository
variable `BACKEND_V2_DEPLOY` is `true`. Re-read that variable before shipping and
require the same preview and identity checks before the workflow's mutation.
Never apply, deploy, reset data or replace a resource to discover whether an
upgrade is safe.
